# ScreenRecorder — аудио: окно настроек, эквалайзер, тестовые записи, папка записей

Инструкция для Hermes DeveloperAgent. Читай целиком до начала работы.

## 1. Роль и цель

Ты — Hermes DeveloperAgent и уже собирал этот проект (см. `Docs/ScreenRecorder_Hermes_DeveloperAgent.md`).
Твоя задача сейчас: принять готовый пакет изменений из этого архива, собрать проект, исправить всё, что не соберётся или не заработает, проверить и доложить реальные результаты.

**Зачем это нужно.** При записи голоса через гарнитуру, подключённую к телефону (звук идёт на ПК через iVCam), Bandicam пишет чистый звук, а ScreenRecorder — рваный, с потрескиванием. Причина не подтверждена: вероятные кандидаты — нехватка времени у потока захвата (нагрузка CPU от захвата экрана и libx264), мелкий буфер WASAPI (50 мс) у «сетевого» виртуального драйвера, запись на диск прямо в потоке захвата. Поэтому пакет делает две вещи:
1. снижает вероятность потери пакетов (очередь + отдельный поток записи, повышенный приоритет потока захвата, настраиваемый буфер, пониженный приоритет ffmpeg);
2. даёт пользователю инструменты, чтобы найти причину самому: окно настроек звука, запись только звука без видео, raw-копия потока устройства, анализатор щелчков/провалов, сравнение с файлом Bandicam.

Дополнительно: выбор папки записей по умолчанию во вкладке Recordings.

## 2. Что уже проверено автором пакета, а что нет

Честно, чтобы ты не принял непроверенное за проверенное.

**Проверено (на Linux, .NET 8 SDK, исходники NAudio 2.2.1):**
- `ScreenRecorder.Core` и весь код `Infrastructure/Audio`, `Infrastructure/Encoding`, `Infrastructure/Recording` компилируются без ошибок.
- Самотест `tools/AudioChainSelfTest` (30 проверок) проходит: ресемплинг 48k/44.1k/16k/8k в обе стороны без разрывов и независимо от размера пакетов, усиление, эквалайзер, фильтр НЧ, режимы каналов, форматы 16/24/32f, анализатор (находит провал, щелчки, клиппинг), нормализация и клонирование настроек.
- В ходе тестов найден и исправлен реальный дефект: WDL-ресемплер при апсемплинге применяет выходной IIR-фильтр с нулевого индекса буфера, игнорируя смещение, поэтому блоки на смещении оставались нефильтрованными (скачки на границах блоков). `StreamingResampler` всегда вызывает `ResampleOut` с нулевым смещением. Не «упрощай» этот код.
- Все XAML-файлы well-formed (XML).

**НЕ проверено (твоя работа):**
- Сборка WPF-проекта `ScreenRecorder.App` (нет Windows SDK/WPF на машине автора). XAML и ViewModel написаны вручную и не компилировались. Синтаксис C# проверен, семантика (генераторы CommunityToolkit, биндинги) — нет.
- Реальная работа WASAPI с iVCam/Bluetooth-гарнитурой, MMCSS, режимы polling/exclusive, поведение `AutoConvertPcm` при запросе своего формата.
- Интеграция с ffmpeg (склейка, конвертация FLAC/MP3/M4A, `libmp3lame` может отсутствовать в сборке).
- Пороги анализатора щелчков — эвристика, не калибровалась на реальных записях.

## 3. Как применить пакет

Структура архива:
```
HERMES_INSTRUCTIONS.md   — этот файл
README.md                — краткое описание для человека
changes.patch            — git diff относительно коммита ca40d07 (ветка master)
files/                   — те же файлы целиком, с путями относительно корня репозитория
```
Порядок:
1. Убедись, что рабочее дерево чистое (`git status`). Создай ветку `audio-settings`.
2. Применить: либо `git apply --check changes.patch`, затем `git apply changes.patch`; либо скопировать содержимое `files/` поверх репозитория с сохранением путей. Если патч не ложится (репозиторий ушёл вперёд) — копируй файлы и вручную сливай конфликтующие (`MainViewModel.cs`, `MainWindow.xaml`, `RecordingsWindow.xaml`, `App.xaml.cs`), ничего не теряя из чужих изменений.
3. Сборка. `.slnx` читает только свежий SDK (.NET 9.0.200+). Если `dotnet build ScreenRecorder.slnx` не работает, собирай проекты напрямую:
   `dotnet build src/ScreenRecorder.App/ScreenRecorder.App.csproj -c Release` и `dotnet build tools/AudioChainSelfTest -c Release`.

## 4. Ограничения (не нарушать)

- Платформа и архитектура — как в `Docs/ScreenRecorder_Hermes_DeveloperAgent.md`: Windows 10 x64, `net8.0-windows`, WPF, MVVM, DI. `ScreenRecorder.Core` не зависит от WPF/NAudio/FFmpeg. UI не вызывает WASAPI/ffmpeg напрямую (только через интерфейсы Core).
- Новые NuGet-пакеты не добавлять. Используются NAudio 2.2.1 (`NAudio.Core` даёт `BiQuadFilter`, `WdlResampler`, `WaveFileReader/Writer`), CommunityToolkit.Mvvm 8.2.2.
- ffmpeg запускать только через `FfmpegRunner` / `ProcessStartInfo.ArgumentList`. Никакой склейки аргументов в строку и `cmd.exe`.
- Комментарии в коде — по-русски (как в репозитории). Строки интерфейса — английские (как в репозитории).
- Не заявляй, что функция работает, пока не запустил. Что нельзя проверить без Windows и устройств — помечай «требует ручной проверки».
- Не удаляй и не переписывай чужие файлы без необходимости. Файлы из `Docs/Claude`, `Docs/ChatGPT` не трогать.

### Ключевые решения (не менять без причины)
1. **Поток захвата делает минимум**: копирует пакет в `BlockingCollection`, считает паузы между пакетами. Конвертация, фильтры, ресемплинг и диск — в потоке `AudioWriter`.
2. **Микрофон не заполняется тишиной посреди записи** — только до первого пакета и в хвосте. Системный звук (loopback) заполняется по часам, потому что WASAPI не шлёт пакеты в тишине.
3. **Фильтры считаются на частоте источника**; полосы выше 0.45·Fs пропускаются.
4. **Запасной вариант запуска**: если выбранный режим/формат не стартует, захват повторяется в shared+event с форматом драйвера, причина пишется в лог.
5. **Исправлено** (не относится к звуку, но мешало): после `LoadAudioDevices()` выбор сбрасывался на «No Audio» и затирал `LastAudioDevice`, поэтому последнее устройство не восстанавливалось.

## 8. Как пользователю искать причину треска (для README и отчёта)

1. Audio Settings → Test and diagnostics, источник — iVCam microphone, включить «Save raw copy». Записать 20–30 секунд речи.
2. Послушать **raw**. Если raw уже трещит — причина в драйвере/транспорте (iVCam, Bluetooth-профиль HFP, Wi-Fi), а не в обработке. Тогда пробовать: режим polling, буфер 200–300 мс, свой формат драйвера 48000/16/1 или 16000/16/1 (родная частота HFP-гарнитуры), другой канал iVCam (USB вместо Wi-Fi).
3. Если raw чистый, а processed трещит — смотреть выходной формат/частоту/эквалайзер; «Re-process raw» позволяет подбирать параметры без перезаписи.
4. Если тест чистый, а запись видео трещит — виновата нагрузка: уменьшить FPS/область, оставить включённым пониженный приоритет ffmpeg и повышенный приоритет потока захвата, увеличить буфер.
5. «Analyze file...» на тех же 30 секундах из Bandicam и из ScreenRecorder: сравнить `Suspected clicks per minute` и `digital-silence dropouts`. Поле `late callbacks` и `max gap` в статистике показывает, голодал ли поток захвата.

## 9. Чего не делать

- Не возвращать `WaveInEvent`/MME-захват: по отчёту проекта он давал худший результат; режим сознательно не реализован.
- Не вызывать `WdlResamplingSampleProvider` и не менять блочную схему `StreamingResampler` (см. раздел 2).
- Не писать на диск и не ресемплировать в обработчике `DataAvailable`.
- Не принудительно задавать 48 кГц драйверу по умолчанию: «формат драйвера» по умолчанию — родной (mix format).
- Не прятать запись: выбранные источники должны быть видны в UI (требование основного ТЗ).
